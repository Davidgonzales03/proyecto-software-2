# HU-20 — Verificación de correo electrónico

**Como** cliente, **quiero** verificar mi correo electrónico mediante un enlace seguro, **para** activar la capacidad de confirmar y realizar pedidos en la tienda.

Issue: #32

## Contexto

Para evitar pedidos con datos falsos o correos inalcanzables, la tienda exige que el Cliente verifique su dirección de correo electrónico antes de poder confirmar un pedido (HU-12). La decisión acordada es **verificar para comprar, no para entrar**:
- La persona puede registrarse, iniciar sesión de inmediato (HU-01 RF-2), explorar el catálogo y armar su carrito.
- Al momento de registrarse, el sistema envía automáticamente un correo con un enlace de verificación de un solo uso.
- Para confirmar un pedido (`POST /api/pedidos`), el correo del cliente debe estar verificado.
- El cliente puede solicitar el reenvío del correo de verificación en cualquier momento desde la pantalla de confirmación o de su cuenta.

Fuentes: issue #32; `CLAUDE.md` → «Correos»; `docs/decisiones.md` → «Registro», «Recuperación de contraseña», «Pedidos».

Decisiones técnicas:
- **Modelo de datos:** Entidad `VerificacionCorreo` (tabla `verificacion_correo`) que almacena el hash SHA-256 del token aleatorio de 256 bits (`SecureRandom`), fecha de emisión, fecha de vencimiento y estado de uso.
- **Campo en usuario:** `correoVerificado` (booleano). Las cuentas preexistentes y el Administrador inicial tienen `correoVerificado = true` por defecto. Los nuevos registros de clientes nacen con `correoVerificado = false`.
- **Vigencia del token:** 24 horas desde su emisión. Un reenvío invalida los tokens pendientes anteriores del mismo usuario.
- **Límite de solicitudes de reenvío:** Máximo 3 solicitudes en 15 minutos por correo/IP (HTTP 429 `SOLICITUDES_EXCEDIDAS`), idéntico al esquema de recuperación de contraseña.
- **Regla en pedidos:** Si un cliente con correo no verificado intenta confirmar un pedido (`POST /api/pedidos`), el backend rechaza la operación con HTTP 409 `CORREO_NO_VERIFICADO`.
- **Ruta frontend:** `/verificar-correo` procesa el parámetro `token` de la URL y confirma la activación en el backend.

## Requisitos funcionales (EARS)

- RF-1: CUANDO un nuevo Cliente completa su registro (`POST /api/auth/registro`), EL SISTEMA crea la cuenta con correo no verificado, genera un token criptográfico de verificación y envía un correo con el enlace de confirmación.
- RF-2: CUANDO un usuario accede al enlace de verificación con un token válido (`POST /api/auth/verificacion-correo`), EL SISTEMA marca el correo del usuario como verificado, invalida el token utilizado y responde confirmando la verificación.
- RF-3: SI un usuario intenta verificar su correo con un token inexistente, expirado (más de 24 horas) o ya utilizado, ENTONCES EL SISTEMA rechaza la solicitud con HTTP 400 `TOKEN_VERIFICACION_INVALIDO`.
- RF-4: CUANDO un Cliente con correo no verificado intenta confirmar un pedido (`POST /api/pedidos`), EL SISTEMA rechaza la confirmación con HTTP 409 `CORREO_NO_VERIFICADO`.
- RF-5: CUANDO un Cliente autenticado solicita el reenvío del correo de verificación (`POST /api/auth/verificacion-correo/reenvio`), EL SISTEMA genera un nuevo token, invalida los pendientes y envía el nuevo correo.
- RF-6: SI se solicitan más de 3 reenvíos de correo de verificación para el mismo usuario o IP en 15 minutos, ENTONCES EL SISTEMA rechaza la solicitud con HTTP 429 `SOLICITUDES_EXCEDIDAS`.
- RF-7: MIENTRAS un Cliente tenga su correo sin verificar, la pantalla de confirmación de pedido (`/confirmar-pedido`) muestra un aviso destacado impidiendo la confirmación y ofreciendo el botón «Reenviar correo de verificación».
- RF-8: Las cuentas existentes previas y el Administrador inicial se consideran verificadas por defecto (`correoVerificado = true`).

## Escenarios

### Registro y recepción de correo (RF-1)
- **Dado** un visitante que completa el formulario de registro con datos válidos
- **Cuando** se crea su cuenta
- **Entonces** ingresa a la tienda con sesión activa y recibe un correo titulado «Confirma tu correo electrónico en Tienda Montero» con su enlace único de verificación.

### Verificación exitosa (RF-2)
- **Dado** un token de verificación recién generado
- **Cuando** el usuario ingresa al enlace `/verificar-correo?token=...`
- **Entonces** el sistema valida el token, actualiza la cuenta a correo verificado y muestra el mensaje de éxito invitándolo a comprar.

### Intento de compra sin verificar correo (RF-4, RF-7)
- **Dado** un cliente con correo no verificado que tiene productos en su carrito
- **Cuando** ingresa a `/confirmar-pedido`
- **Entonces** visualiza el aviso «Debe verificar su correo antes de poder realizar pedidos» y no puede confirmar la compra hasta verificarlo.

### Token vencido o reutilizado (RF-3)
- **Dado** un token generado hace más de 24 horas o ya utilizado
- **Cuando** el usuario intenta verificar su correo con ese token
- **Entonces** el sistema muestra «Este enlace ya no sirve o ya fue utilizado» y ofrece la opción de reenviar uno nuevo.
