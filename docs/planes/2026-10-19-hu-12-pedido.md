**Lo delicado: la confirmación.** Una sola transacción, con los bloqueos
siempre en el mismo orden (cliente y después productos por id ascendente),
así dos confirmaciones no se traban entre sí ni con el inventario (RF-7):

```java
@Transactional
public PedidoResponse confirmar(Long idUsuario, ConfirmacionRequest solicitud) {
	Usuario cliente = usuarioRepository.findConBloqueoByIdUsuario(idUsuario).orElseThrow();
	vencerSiCorresponde(idUsuario); // RF-5: uno vencido no bloquea
	pedidoRepository.findFirstByUsuario_IdUsuarioAndEstado(idUsuario, PENDIENTE_PAGO)
			.ifPresent(p -> { throw new PedidoPendienteException(p.getIdPedido()); });
	List<LineaCarrito> lineas = lineaCarritoRepository.findByUsuario...(idUsuario);
	if (lineas.isEmpty()) throw new CarritoVacioException();
	// Productos bloqueados en orden de id: el mismo orden que cualquier otra confirmación
	Map<Long, Producto> productos = new TreeMap<>();
	for (Long id : lineas.stream().map(l -> l.getProducto().getIdProducto()).sorted().toList()) {
		productos.put(id, productoRepository.findConBloqueoByIdProducto(id).orElseThrow());
	}
	List<FaltaDeStock> faltas = revisar(lineas, productos); // todas, no solo la primera (RF-3)
	if (!faltas.isEmpty()) throw new StockInsuficienteException(faltas);
	BigDecimal total = total(lineas, productos);
	if (total.compareTo(solicitud.totalEsperado()) != 0) throw new TotalCambiadoException(total); // RF-15
	LocalDateTime ahora = LocalDateTime.now(clock);
	Pedido pedido = Pedido.confirmar(cliente, lineas, productos, solicitud, ahora, ahora.plus(VIGENCIA));
	pedidoRepository.save(pedido);
	for (LineaPedido linea : pedido.getLineas()) {
		Producto producto = productos.get(linea.getProducto().getIdProducto());
		BigDecimal nuevo = producto.getStock().subtract(linea.getCantidad());
		producto.aplicarMovimiento(nuevo); // nunca negativo: ya se revisó con el bloqueo puesto
		movimientoRepository.save(MovimientoStock.reserva(producto, linea.getCantidad(), nuevo, pedido, ahora));
	}
	lineaCarritoRepository.deleteByUsuario_IdUsuario(idUsuario);
	return PedidoResponse.from(pedido, retiro());
}
```

`vencerSiCorresponde` corre dentro de la transacción de `confirmar`: si la
confirmación falla (por ejemplo, sin stock), el vencimiento se revierte con
ella. Es inofensivo: la tarea programada lo vuelve a hacer.

**Lo delicado: cancelar y vencer.** Los dos terminan en `liberar`, con los
bloqueos en el mismo orden que `confirmar` (cliente, pedido, productos por
id), y el estado se revisa con el pedido ya bloqueado: el que llega segundo
no libera dos veces (RF-12):

```java
@Transactional
public CancelacionResponse cancelar(Long idUsuario, Long idPedido) {
	Pedido pedido = bloquear(idUsuario, idPedido); // de otro cliente o inexistente: 404 (RF-13)
	if (pedido.getEstado() != PENDIENTE_PAGO) throw new PedidoNoPendienteException(); // RF-12
	int noVolvieron = liberar(pedido, EstadoPedido.CANCELADO);
	return new CancelacionResponse(PedidoResponse.from(pedido, retiro()), noVolvieron);
}

// La tarea programada: si ya se canceló o venció, no hace nada (RF-12)
@Transactional
public void vencer(Long idUsuario, Long idPedido) {
	Pedido pedido = bloquear(idUsuario, idPedido);
	if (pedido.getEstado() == PENDIENTE_PAGO && !pedido.getVence().isAfter(LocalDateTime.now(clock))) {
		liberar(pedido, EstadoPedido.VENCIDO);
	}
}

// Cliente y después pedido: el mismo orden que confirmar
private Pedido bloquear(Long idUsuario, Long idPedido) {
	usuarioRepository.findConBloqueoByIdUsuario(idUsuario).orElseThrow(PedidoNoEncontradoException::new);
	return pedidoRepository.findConBloqueoByIdPedidoAndUsuario_IdUsuario(idPedido, idUsuario)
			.orElseThrow(PedidoNoEncontradoException::new);
}

// Productos por id ascendente, como al confirmar. Devuelve cuántas líneas no volvieron al carrito (RF-16)
private int liberar(Pedido pedido, EstadoPedido estadoFinal) {
	LocalDateTime ahora = LocalDateTime.now(clock);
	for (LineaPedido linea : pedido.lineasPorProducto()) { // ordenadas por idProducto
		Producto producto = productoRepository.findConBloqueoByIdProducto(linea.getIdProducto()).orElseThrow();
		BigDecimal nuevo = producto.getStock().add(linea.getCantidad());
		// Sin el tope de las entradas: devolver lo reservado no se rechaza. Si entradas posteriores dejaron el
		// stock cerca de 9 999 999,99 y la columna no lo admite, la transacción falla, queda en el log y la tarea
		// lo reintenta (caso improbable, anotado)
		producto.aplicarMovimiento(nuevo);
		movimientoRepository.save(MovimientoStock.liberacion(producto, linea.getCantidad(), nuevo, pedido, ahora));
	}
	if (estadoFinal == EstadoPedido.CANCELADO) pedido.cancelar(ahora); else pedido.vencer(ahora);
	return carritoService.devolver(pedido.getUsuario(), pedido.getLineas()); // RF-11, RF-16; cliente ya bloqueado
}
```

`VencimientoPedidos` es **otro bean**: llamar a un método `@Transactional`
del mismo bean no abre transacción, y cada pedido tiene que vencer en la
suya, para que uno que falla no frene a los demás:

```java
@Component
class VencimientoPedidos {
	@Scheduled(fixedDelayString = "PT1M")
	void vencer() {
		for (PedidoAVencer p : pedidoRepository.findByEstadoAndVenceLessThanEqual(PENDIENTE_PAGO,
				LocalDateTime.now(clock))) { // proyección: idPedido e idUsuario
			try {
				pedidoService.vencer(p.idUsuario(), p.idPedido()); // una transacción por pedido
			} catch (RuntimeException e) {
				log.warn("No se pudo vencer el pedido {}", p.idPedido(), e);
			}
		}
	}
}
```

Además, leer el carrito, confirmar o abrir un pedido vencen primero el del
cliente si ya pasó la hora (`vencerSiCorresponde`, con el cliente ya
bloqueado): el cliente nunca ve «Pendiente» con el tiempo agotado (RF-10).
Por eso `CarritoService.ver` pasa a ser una transacción de escritura.
`VIGENCIA` = 30 minutos, en el servicio.

## Decisiones del plan

- **Bloqueos en un solo orden** (cliente, pedido, productos por id): las
  confirmaciones, las cancelaciones, los vencimientos y el inventario nunca
  se esperan en círculo.
- **El vencimiento, doble:** la tarea programada cada minuto libera el stock
  aunque nadie mire, y la lectura vence en el acto el pedido del cliente que
  la pide. Con H2 en las pruebas, el `Clock` fijo reemplaza la espera.
- **El total esperado lo manda el cliente solo para comparar:** el pedido se
  arma siempre con los precios del servidor.
- **`idPedidoPendiente` en el carrito** en vez de otro endpoint: el carrito
  ya se pide en cada página que lo necesita. Es un campo nuevo en la API de
  HU-11, aditivo: no cambia su comportamiento.
- **Rutas del cliente con `mis-`:** `mis-pedidos/:id` (y la lista de HU-14 en
  `mis-pedidos`), como `mis-datos`; así no chocan con las pantallas del
  personal de HU-17.
- **Las líneas que no vuelven se cuentan solo al cancelar:** al vencer no hay
  a quién avisar.

### Distinto de lo planeado

- La devolución de las líneas al carrito está en `PedidoService` y no en
  `CarritoService.devolver`: el carrito ya usa el servicio de pedidos para
  vencer y saber si hay uno pendiente, y al revés sería una dependencia
  circular.
- `PedidoResponse` suma `segundosParaPagar`, calculado en el servidor: el
  contador no depende del reloj ni de la zona del dispositivo.
- `ClockConfig` en microsegundos, la precisión de las columnas: con más
  decimales la base redondeaba y el pedido no vencía justo a los 30 minutos.
- En el carrito, «Confirmar pedido» aparece solo si todas las líneas se
  pueden comprar (el plan decía «si hay líneas que se pueden comprar»): el
  backend rechaza todo o nada.
- La confirmación lee los pendientes sin bloqueo y lo devuelto se recorta al
  máximo (revisión; ver arriba).
